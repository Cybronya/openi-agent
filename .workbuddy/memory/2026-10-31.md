## 网页操作能力测试（OpenI 站点）

**目标**：验证能否操作网页并读取页面信息，测试站点 `https://openi.pcl.ac.cn/cloudbrains`。

**结论**：可行。采用 Chrome DevTools Protocol (CDP) 直连方案。

### 技术方案
- 以 `--remote-debugging-port=9222 --remote-allow-origins=* --user-data-dir=<临时目录>` 启动独立 Chrome 实例
- 通过 `http://127.0.0.1:9222/json/list` 发现页面目标，WebSocket 直连下发 CDP 指令
- 客户端工具：`F:\openi\cdp.py`，子命令 `read / shot / click / type / nav / eval / list`
- 依赖：仅 `websockets`（其余用 Python 标准库）

### 关键踩坑
1. **本地请求被代理劫持**：环境变量 `HTTP_PROXY=127.0.0.1:58897` 导致访问 127.0.0.1:9222 返回 502。解法：`urllib.request.build_opener(urllib.request.ProxyHandler({}))` 绕过。
2. **PowerShell `Start-Process` 启动的 Chrome 立即退出**：需用 Bash 后台任务方式启动。
3. **Cookies 库被 Chrome 独占锁定**：`cp`/`robocopy /B`/Win32 CreateFileW 均失败（error 32）。解法：WMI `Win32_ShadowCopy.Create` 建卷影副本，再从 `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyN\...` 用 `.NET File.Copy` 提取。
4. **Chrome 156 app-bound 加密**：`os_crypt.app_bound_encrypted_key` 保护主密钥，外部无法解密 Cookie 明文。
5. 本机**无 Node.js**，官方 agent-browser 插件与 Playwright 路径均不可用；PyPI 下载 playwright 超时 10 分钟。CDP 是最可靠路径。

## 追加：可行性追问与登录态攻坚（23:03 - 23:20）

用户追问四个问题：能否直接操作他已打开的页面、独立 Chrome 是什么、是否新增程序、磁盘占用。

### 决定性发现：Chrome 136+ 官方屏蔽默认 profile 调试端口
搜到 Google 官方博客（developer.chrome.com/blog/remote-debugging-port）确认：
自 Chrome 136 起，若 `--user-data-dir` 指向**默认数据目录**，`--remote-debugging-port` 与
`--remote-debugging-pipe` **被直接忽略**，CDP 端点根本起不来。

→ 用户日常那个 Chrome（桌面快捷方式启动，无调试参数）**无法被接入**，
  事后也无法补救，只能带调试参数重启。这是官方为防静默接管登录态浏览器而堵的路。

### 登录态攻坚：三次尝试全部失败，根因已定位
1. 复制 profile（`cp -r`）→ Cookies 库被 Chrome 独占锁，error 32，cp/robocopy /B/Win32 CreateFileW 全部失败
2. 解密 Cookie → Chrome 156 主密钥是 `app_bound_encrypted_key`（app-bound 加密），外部无法解密
3. NTFS 卷影副本（`Win32_ShadowCopy.Create` → `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopyN\`）
   提取 Cookies + Local State 成功 → 注入后 `i_like_openi` 仍 401

**根因（通过 Cookie 表结构分析定位）**：
- `gitea_incredible` / `gitea_awesome`（remember-me 令牌，persist=1，有效期到 11/28）
  在**新 profile 目录中因 app-bound 密钥不同而被 Chrome 启动时丢弃**
- `i_like_openi` 是 session cookie（`is_persistent=0`），且服务端在轮换会话
  （22:31 快照与 23:08 快照拿到的会话密文不同）
→ 结论：登录态无法通过复制 profile 迁移，只能用户手动登录一次

## 追加三：autoConnect 实测打通，接管用户已登录浏览器（23:36 - 23:58）

用户开启 `chrome://inspect/#remote-debugging` 后，`DevToolsActivePort` 文件生成，
autoConnect 通道打通 —— **成功接管用户正在运行的浏览器，完全共享登录态**。

### 机制
Chrome 144+ 在用户显式开启远程调试后，于默认 profile 生成两行文件：
```
64911
/devtools/browser/26bb7c00-91d4-4cbc-bea3-f039f7b25b92
```
读出后拼 `ws://127.0.0.1:64911/devtools/browser/<id>` 直连。

### 坑 1：Origin 头必须严格等于 http://127.0.0.1:<port>
实测枚举（这是最关键的发现，Python 客户端默认行为直接失败）：
| Origin | 结果 |
|--------|------|
| `http://127.0.0.1:64911` | ✅ 101 Switching Protocols |
| `http://localhost` | ❌ 403 |
| `http://localhost:9222` | ❌ 403 |
| `chrome://inspect` | ❌ 403 |
| `devtools://devtools` | ❌ 403 |
| `null` | ❌ 403 |
| 不带 Origin | ❌ 握手挂起超时 |

Python `websockets` 默认不带 Origin → 握手超时；Node 手写握手（不带 Origin）却能成功，
说明 Chrome 对 autoConnect 端点有特殊 Origin 校验逻辑。

### 坑 2：同时只允许一个 autoConnect 客户端
上一连接未释放时新握手一直挂起（`opening handshake timeout`）。
表现为「有时能连上，有时超时」，非常容易误判。解法：长间隔多次重试（10 次 × 3s）。

### MCP 侧的两个配置坑
1. **必须用 `node` 直接启动 MCP 入口，不能用 `npx`**
   npx 把带空格的 `--userDataDir=C:\...\Chrome\User Data` 截断成 `...\Chrome\User`，
   报 ENOENT。改用 `node <绝对路径>/chrome-devtools-mcp.js` 解决。
2. **必须加 `--allow-unrestricted-paths`**
   否则 MCP 文件写入被限制在 OS 临时目录，写工作区报 "Access denied: not within
   any of the configured workspace roots"。
